# Verifying Praman evidence — without trusting Praman

This document explains how to independently confirm that a Praman evidence
bundle is genuine: unaltered, correctly chained, and signed by the key its
`key_id` claims. Every value below was generated by this repository's own
code and is reproducible — run the commands yourself and you will get the
same numbers.

There are three ways to verify a bundle, in increasing order of
independence from Praman's own infrastructure:

1. **In your browser**, using the "Verify this yourself" panel on the
   [live demo](https://praman-evidence-engine.vercel.app) — native
   WebCrypto, no server-side trust required once the bundle and public key
   are fetched.
2. **Offline, with the standalone script** — `scripts/verify_bundle.py`,
   which does not import anything from this repository's `praman` package.
3. **By hand**, following the worked example below — no code at all,
   just SHA-256, HMAC-SHA256, and Ed25519, computed however you like.

## What "independent" actually means here

A verification feature that asks you to trust our server to tell you
whether it is being honest has not solved anything. Every check described
here is designed so that:

- The **root** is recomputed from raw event data you fetched yourself, not
  copied from a field the server also filled in.
- The **signature** is checked against the root **you** recomputed, never
  the root the server claims — verifying a server's own number against the
  server's own signature proves the server can multiply, nothing else.
- The **canonical JSON** for each event is the exact byte sequence that was
  hashed; re-serialising it must reproduce identical bytes, or a genuine
  bug looks identical to tampering.

See `docs/ADR/0016-client-side-verification.md` for the full design
rationale.

## The disclosed limitation this depends on

This demo build uses **one fixed, disclosed HMAC key** — 32 zero bytes —
for every tenant, not a real per-tenant key (see `docs/LIMITATIONS.md`).
That is precisely why a verifier outside Praman can recompute HMACs at
all: the key is public knowledge for this build. A production deployment
using real per-tenant keys would not publish them, and bundle-based
HMAC-chain verification by an outside party would not be possible without
that tenant's own key. The Merkle root and Ed25519 signature checks do
not depend on this and remain independently verifiable regardless.

## Bundle format

`GET /evidence/bundle` (header `X-Tenant-ID: <your tenant>`) returns:

```json
{
  "bundle_version": "1.0",
  "tenant_id": "demo-a1b2c3d4",
  "generated_at": "2026-08-16T14:40:00+00:00",
  "algorithms": {
    "canonicalisation": "RFC 8785-style JCS (sorted keys, compact separators, NFC unicode)",
    "leaf_hash": "SHA-256 with 0x00 domain-separation prefix",
    "node_hash": "SHA-256 with 0x01 domain-separation prefix",
    "signature": "Ed25519",
    "hmac_chain_key": "STUB: fixed 32-byte all-zero key, disclosed in docs/LIMITATIONS.md"
  },
  "events": [
    { "sequence": 0, "canonical_json": "<exact bytes that were hashed>", "hmac_value": "<hex>" }
  ],
  "merkle_root": "<hex>",
  "signature": "<hex>",
  "key_id": "<hex>",
  "verification_instructions_url": "https://github.com/omdch26/praman-evidence-engine/blob/main/docs/VERIFICATION.md"
}
```

`GET /keys/public` (no auth required) returns the matching public key:

```json
{
  "key_id": "<hex, matches the bundle>",
  "algorithm": "Ed25519",
  "public_key_pem": "-----BEGIN PUBLIC KEY-----\n...\n-----END PUBLIC KEY-----\n",
  "public_key_raw_hex": "<32 bytes, hex — the form WebCrypto's importKey expects>"
}
```

## Worked example, by hand

Two events, real values, generated with this repository's own domain
functions (`praman/domain/canonical.py`, `praman/domain/hashing.py`,
`praman/domain/merkle.py`).

### Step 1 — canonical JSON

Event 1:
```json
{"action":null,"event_type":"consent_granted","module":"privacy","payload":{},"principal_id_hash":"sha256:abc123","timestamp":"2026-08-16T14:30:00"}
```

Event 2:
```json
{"action":null,"event_type":"consent_withdrawn","module":"privacy","payload":{},"principal_id_hash":"sha256:abc123","timestamp":"2026-08-16T14:35:00"}
```

Keys sorted alphabetically, no insignificant whitespace, UTF-8 bytes. This
is the exact byte sequence — reserialising the same dict on any machine
reproduces these bytes exactly, which is the whole point of
canonicalisation (see `domain/canonical.py`'s docstring).

### Step 2 — HMAC-SHA256, chained

Using the disclosed fixed key (32 zero bytes):

```
event 1 HMAC (no previous — first event):
  HMAC-SHA256(key, canonical_json_1)
  = bb5fc137d94d13cf41dd1808ba87f90a926f22e44bb2cae84b200c63b67d6007

event 2 HMAC (chained to event 1):
  HMAC-SHA256(key, hex_to_bytes(event_1_hmac) + canonical_json_2)
  = 17ec0053e84eb4d33c8c33daf22e10261fe8343a49e48d6b367431f89816b250
```

Note event 2's HMAC input is the **bytes** of event 1's hex HMAC
(32 bytes), concatenated with event 2's canonical JSON bytes — not the
hex string. Get this wrong and every HMAC after the first will silently
fail to match.

### Step 3 — Merkle leaves and root

Leaf hashing prefixes each HMAC's raw bytes with `0x00` before SHA-256:

```
leaf_1 = SHA-256(0x00 || hex_to_bytes(event_1_hmac))
       = 73e3f4bbcd05112fcc9fb3592e7e2f00bb03f5da5d10fc7032d2a108313119a2

leaf_2 = SHA-256(0x00 || hex_to_bytes(event_2_hmac))
       = bf6279ecc9f5838b5087b56f33b9af74b20c5848239b017716338a18458bc061
```

With exactly two leaves, the root is one internal node, prefixed `0x01`:

```
root = SHA-256(0x01 || leaf_1 || leaf_2)
     = 887e6816b035be9def1ba330b6b7f78e0a36a8ae5f119d7749905dc7cd80d7ae
```

**Why the prefixes matter:** without domain separation between leaf and
internal-node hashing, an attacker can present an internal node as if it
were a leaf and forge an inclusion proof — the second-preimage weakness in
the original Bitcoin Merkle construction (CVE-2012-2459). See
`docs/ADR/0002-merkle-over-blockchain.md` and `domain/merkle.py`.

For an odd number of events, the last leaf is duplicated before hashing
(the Certificate Transparency convention) rather than left unpaired.

### Step 4 — signature

The root (32 raw bytes, not the hex string) is signed with Ed25519:

```
signature = Ed25519_Sign(private_key, root_bytes)
```

To verify, given the bundle's claimed `signature` and the public key from
`GET /keys/public`:

```
Ed25519_Verify(public_key, signature, YOUR_recomputed_root_bytes)
```

**Verify against the root you just computed in Step 3, not the bundle's
`merkle_root` field.** If those two roots differ, the signature check
must use your own — checking the server's signature against the server's
own claimed root only proves the server's arithmetic is self-consistent,
not that the events weren't altered before the root was computed.

## Verifying with the standalone script

```bash
# 1. Fetch a bundle and the public key
curl -s -H "X-Tenant-ID: demo-a1b2c3d4" https://praman-evidence-engine.onrender.com/evidence/bundle > bundle.json
curl -s https://praman-evidence-engine.onrender.com/keys/public | python -c "import json,sys; print(json.load(sys.stdin)['public_key_pem'])" > key.pem

# 2. Verify entirely offline
python scripts/verify_bundle.py bundle.json --public-key key.pem
```

Output:

```
Verifying bundle for tenant demo-a1b2c3d4 (6 events, key_id 539693f825f9515d)

  [PASS] hmac_chain_continuity: Every event's HMAC matches its canonical JSON and the chain.
  [PASS] merkle_root_matches: Recomputed root matches the bundle's claimed root.
  [PASS] signature_valid: Signature verifies against the independently recomputed root.

PASSED
```

Exit code `0` on a full pass, `1` if any check fails — script-friendly for
CI or a batch-verification job. `scripts/verify_bundle.py` deliberately
does **not** import anything from the `praman` package (verified by
`tests/scripts/test_verify_bundle.py::test_script_does_not_import_praman`)
— a verifier sharing code with the system it verifies proves less than an
independent reimplementation of the same specification.

## Verifying in your browser

Open the [live demo](https://praman-evidence-engine.vercel.app), generate
a scenario, then use the "Verify this yourself" panel. It performs the
exact four steps above using `crypto.subtle` — native WebCrypto, no
external library — and shows each intermediate value as it computes it.
View source on the page to read the actual verification code; it is not
minified or bundled.

If your browser does not support Ed25519 in WebCrypto (older Safari,
some older Chromium builds), the HMAC-chain and Merkle-root checks still
run — SHA-256 is universally supported — and the signature step is shown
as unsupported, not silently skipped.

## What this does and does not prove

**Proves:** the events in the bundle are exactly what was hashed, the
Merkle root correctly commits to all of them, and the signature is
genuine for the key identified by `key_id`.

**Does not prove:** that the timestamp on any event is accurate. This
build's timestamps are self-asserted from the server's system clock (see
`docs/LIMITATIONS.md` — RFC 3161 external timestamping is designed but not
implemented). A vendor who controlled both the ledger and the clock could,
in principle, re-sign a doctored history with a plausible-looking
timestamp. External timestamp anchoring is what closes that specific gap,
and it is not built yet. Say so plainly if asked — a vendor who cannot
name their own unverified assumption has not looked for it.
