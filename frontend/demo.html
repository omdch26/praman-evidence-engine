The Problem

"Prove this AI decision wasn't tampered with."

A bank approves a loan using an AI system. A customer later disputes the decision. The regulator asks a simple question: how do you know your own team didn't quietly edit the record after the fact? A database row isn't an answer. Whoever controls the database can edit it. Praman replaces "trust us" with a chain of events that makes editing detectable within milliseconds — and this page proves it against the real backend, not a mockup. This isn't really a banking problem — it's what happens anywhere a decision affects someone and could later be challenged: an AI that screens job applicants, flags an insurance claim, or triages a patient faces the same question. Banking just has the regulation first.

Why this is live now, not hypothetical: DPDP Rules 2025 were notified 14 Nov 2025, with enforcement phasing through Nov 2026 and May 2027. The Consent Manager framework is being operationalised between June and Aug 2026, right now. RBI's FREE-AI Framework, released Aug 2025, requires every regulated entity to run a board-approved AI policy with lifecycle governance. Both created a live compliance gap that most banks are still solving with spreadsheets.

Module 2 · AI Governance

Was the AI allowed to make this call?

Every AI decision is checked against its assigned autonomy tier before it's allowed to act. That's the same tier shown in the scenario above.

RBI FREE-AI mapping: autonomy tiers plus this pass/fail check implement Pillar-level requirements from the FREE-AI Framework (7 Sutras / 6 Pillars / 26 Recommendations, Aug 2025) for structured governance across the AI lifecycle. The requirement is specific: AI actions have to stay within a board-approved policy boundary. "The model seemed fine" isn't a policy.

Product Maturity

What's built, what's honest, what's next

This is an MVP build. Rather than blur the line between working and aspirational, every stub is disclosed in the code and here. Click through:

Append-only event ledgerLive
A Postgres trigger physically blocks UPDATE and DELETE. Records cannot be quietly rewritten, even by a database administrator.
This is enforced at the database layer, not application logic. An app-layer guard is bypassable by anyone with direct DB access, and that's exactly the threat model here. The "Try to edit the database" button above issues a real UPDATE and shows you Postgres's own rejection.
HMAC chaining across both modulesLive
Every event is cryptographically linked to the one before it. Governance decisions from Module 2 chain into the same ledger as privacy events from Module 1.
domain/hashing.py. The client holds the key, so the vendor cannot forge an event even with full database access.
Merkle tree, root, and inclusion proofsLive
Prove one specific event is in the record without disclosing any of the others.
domain/merkle.py. Leaves are prefixed 0x00, internal nodes 0x01, domain-separated to close the second-preimage weakness in the original Bitcoin construction (CVE-2012-2459).
Ed25519 signing with a stable keyLive
The root is signed with a key that does not change between requests. Anyone holding the public key can verify it independently, including a regulator, without trusting the bank.
Behind a KeyCustody port (ports/key_custody.py). ECDSA P-256 and an HSM/KMS path are documented alternatives; swapping is one branch in factories.py. See ADR 0014 — this used to generate a fresh, unpublished key per request, which meant no signature could ever be checked.
BSA §63 certificate generationLive
Produces a PDF in the "Certificate by Party" format: identifies the record, how it was produced, and its hash value and algorithm.
BSA 2023 came into force 1 July 2024, replacing the Indian Evidence Act 1872. §63 recognises two certificate types; this generates the party certificate, leaving Part B for the customer's CTO to attest.
Autonomy tiers + delegation ceilingsLive
Four tiers from read-only to unrestricted. An agent cannot spawn a second agent with more authority than it holds itself.
Most AI-agent frameworks miss this entirely: an ACT_BOUNDED agent spawning an ACT_FULL child would silently defeat the whole tier system. Blocking that kind of privilege escalation through delegation is the point.
Circuit breaker with halt-as-evidenceLive
When a threshold trips, the agent halts and falls back to human review. The halt itself is written to the ledger as evidence the control worked.
The halt is logged before fallback, so a regulator can see the safety mechanism firing, not just its aftermath.
Multi-tenant isolation + OpenTelemetryLive
Each tenant's ledger is separate. Tracing runs VPC-internal with no prompt content leaving the perimeter.
Prompts and completions are never exported. gen_ai.* attributes stay isolated in the adapter layer, so observability doesn't quietly become a data-egress path.
These three are deliberately incomplete. The interfaces exist and the mechanisms around them work — the implementations behind them are placeholders, and shipping them as "done" would be the kind of undisclosed gap that costs a vendor its credibility on the first technical review.
Drift detectionDeterministic stubReal detector: Month 2
Returns a reproducible score so demos are stable, but it measures nothing real. The circuit-breaker mechanism it feeds is fully working. Only the detection is placeholder.
adapters/drift/deterministic_stub.py. Production needs population stability index over a rolling reference window, plus semantic entropy for free-text outputs, which requires multiple sampled generations per call. That's a real latency and cost decision, not a weekend feature. Do not run Module 2 drift in production on this build; the stub will never trip.
Per-tenant HMAC keysFixed demo keyMonth 2
Currently one fixed key for every tenant. Enough to demonstrate chaining, not enough for real evidentiary separation between tenants. This is also why your browser can recompute HMACs itself in the "Verify this yourself" panel above — it only works because the demo key is intentionally public.
Module 1 and Module 2 must chain with the same key or the chain breaks at the module boundary, so this is a key-custody design decision, not a one-line fix. It's deferred deliberately rather than decided prematurely.
RFC 3161 timestampingLocal clockMonth 3
Timestamps are currently self-asserted from the system clock. Under adversarial cross-examination that's the weakest link in the chain, and we'd rather say so than let a reviewer find it. A vendor who controlled both the ledger and the clock could, in principle, re-sign a doctored history after the fact — external anchoring is what closes that gap, and it is not built yet.
adapters/anchor/rfc3161_freetsa.py is designed but not implemented. It needs TSA selection, TLS, certificate validation, and outage handling. Until then, "when the root existed" rests on the bank's own clock.
PSI + semantic entropy drift detectorsNextMonth 2–4
Real drift measurement across data distribution, output semantics, and behaviour, replacing the stub behind the same interface.
Swapping is one branch in factories.py. Nothing else in the system changes, because that's what the port is for.
